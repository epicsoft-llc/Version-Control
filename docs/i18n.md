# Translations

The interface exists in English and German. **English is the default and the fallback** — it is what a
reader gets when their language has no value for a key.

Both artifacts read the same shape of file: flat JSON, one key per line, no nesting.

| | Backend (`core/`) | Dashboard (`dashboard/`) |
|---|---|---|
| Files | `src/main/resources/messages/{en,de}.json` | `src/assets/i18n/{en,de}.json` |
| Read by | `JsonMessageSource`, a Spring `MessageSource` | ngx-translate |
| Placeholders | `{0}`, `{1}` (`MessageFormat`) | `{{name}}` |
| Used for | notification texts, error messages | everything a person sees |

## Adding a string

1. Pick a key: flat, `{feature}.{sub}.{element}` — `matrix.cell.movingTag`, `component.field.tagPattern`.
   `nav.*` for navigation labels, `error.*` for error messages.
2. Add it in Tolgee, not to the JSON files by hand.
3. Pull the files (below) and commit them.

**Never hand-edit the generated JSON files.** They are regenerated from [Tolgee](https://tolgee.io) and
your edit is overwritten. A committed file that lags behind is expected, not a bug.

Which instance and which project is not described here — it comes from the environment, like every
other piece of configuration.

## Pulling

Both sides fetch the same way and both are no-ops without a token, so the committed files are used as
they are and everyone can build the project:

```bash
./gradlew :core:pullTranslations      # backend
cd dashboard && npm run i18n:pull     # dashboard
```

Both sides need the same three environment variables: `VC_TOLGEE_URL`, `VC_TOLGEE_PROJECT_ID` and
`VC_TOLGEE_API_KEY`. Without the token both commands print one line and change nothing.

Which keys an artifact consumes is decided by its tag — `core` for the backend, `dashboard` for the
frontend. That is a property of the artifact, not of the environment, so each module carries its own:
the backend in `core/build.gradle`, the frontend in `dashboard/scripts/i18n-pull.mjs`. One project
serves both.

## Verifying

```bash
./gradlew :core:verifyTranslations
```

Fails when a key has no value in the fallback language. That check runs as part of `./gradlew check`,
because an empty fallback value produces an empty label — a defect that is otherwise only noticed by
looking at the running application.

The key universe is the union over all languages, so a key that is missing from the English file
entirely is caught as well as one that is present but empty.

That leaves one gap, and it is the one that shows up on screen: a key the **code** asks for and Tolgee
never had is consistent in every language and missing all the same. Nothing reports it — ngx-translate
renders the key itself, and the backend hands it to whoever reads the message. The second check closes
that gap from the other side:

```bash
./gradlew :core:verifyMessageKeys      # backend
cd dashboard && npm run i18n:verify    # dashboard
```

Both run in the pipeline — the backend one hangs off `check`, the frontend one runs right after the
pull, so it judges the files the build actually uses. Both read the sources, collect every key that is
used, and compare against the fallback bundle. Keys
built at runtime are resolved rather than skipped: `"taskSection." + section.name()` is expanded over
the constants of that enum, and `'constraintState.' + check.state` over the members of the TypeScript
union of the same name. A prefix with no such type behind it is an error, not a pass.

## Why the files are flat

The export sends an empty `structureDelimiter`. With a delimiter the export nests on every `.` in a key,
and both consumers — ngx-translate and the JSON `MessageSource` — resolve nothing: the build stays
green and only the interface is empty. Both pull paths reject a nested response instead of writing it.
